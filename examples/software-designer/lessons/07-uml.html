面向对象方法用 UML（Unified Modeling Language，统一建模语言）说话：用例图捕获需求，类图静态建模，行为图刻画动态，设计模式沉淀可复用的方案。下午案例的 UML 补图题 + 上午的模式意图题都从这里出。

一、用例图：需求视角第一张图

用例图三要素：参与者（Actor，系统外部的人/外部系统/定时任务）、用例（参与者可感知的完整功能，椭圆）、系统边界（框住全部用例）。图书借阅系统片段：

        ┌─────────────── 图书借阅系统 ───────────────┐
读者 ───┤ ○ 查询书目   ○ 借书 ◇include◇▶ ○ 校验读者证  │
        │ ○ 还书 ◁extend◇─ ○ 缴逾期罚金 ([已逾期])    │
图书管理员 ─ ○ 登记新书                                 │
        └──────────────────────────────────────────┘

四种关系语义（下午判断题的钉子户）：

关系记法语义
关联实线（可加箭头）参与者与用例的交互
包含 «include»基用例 ─▷ 被包含用例（虚线）无条件执行，基用例每次都跑被包含用例
扩展 «extend»扩展用例 ─▷ 基用例（虚线）有条件才执行，在扩展点插入额外行为
泛化空心三角实线特殊参与者/用例继承一般者

易错点（include vs extend）：箭头方向相反——include 从基用例指向被包含用例，extend 从扩展用例指向基用例。判别口诀：「必发生找包含，不一定发生找扩展」。借书必先校验读者证 → include；只有逾期才缴罚金 → extend。

典型题问法

给一段说明补参与者/用例/关系。三步：① 圈「谁能用系统」（人、外部系统、别忘了定时触发的时钟，如「每晚触发逾期检查」）；② 圈「要完成什么」成用例；③ 按「必做/条件做」定 include / extend。

二、类图：六种关系记法与多重度

类图是静态结构建模的核心。六种关系记法（下午补图题直接考线怎么画）：

泛化  子类 ─────▷ 父类      实线＋空心三角箭头，指向父类（is-a）
实现  类 - - -▷ 接口        虚线＋空心三角箭头，指向接口
组合  整体 ◆──── 部分        实线＋实心菱形，菱形贴整体端（共存亡）
聚合  整体 ◇──── 部分        实线＋空心菱形，菱形贴整体端（可分离）
关联  A ───────── B         实线，可加导航箭头与多重度
依赖  A - - - - -▷ B        虚线箭头，指向被临时使用者（参数/局部）

多重度写在关联线端点：1（恰好一个）、0..1（零或一）、1..*（至少一）、*（任意多）、n..m（n 到 m 个）。

图书借阅类图片段（典型题风格）：读者与借阅记录是关联（1 对 0..*）；借阅记录依赖罚金计算器（临时调用）；书目与馆藏册是聚合（同书目多册，册可单独处理）；订单与订单项是组合（删订单连着删订单项）。

┌────────┐ 1      0..* ┌────────────┐ - - -▷ ┌──────────┐
│ Reader │──────────────│ BorrowRec  │  依赖   │ 罚金计算器 │
└────────┘   发起        └────┬───────┘        └──────────┘
                                │ *         1
                                │ 对应
                         ┌─────▼──────┐◇──────  ┌────────┐
                         │ Book 书目   │  聚合   │ Copy 册 │
                         └────────────┘         └────────┘

辨析锚点：菱形都贴「整体」端——实心=组合（部分随整体生灭：订单—订单项），空心=聚合（部分可独立：车队—汽车）。泛化/实现的三角都是空心且指向抽象端，区别只在实线还是虚线。

三、行为图：序列图 / 状态图 / 活动图辨析

行为图族里最常混的三张图：

图关注什么核心元素典型场景
序列图对象间消息的时间顺序生命线、激活条、同步消息（实心箭头）、返回（虚线箭头）实现一个用例的交互流程
状态图单个对象状态随事件迁移状态、事件、迁移、[条件]、entry/exit、组合状态订单/借阅记录的生命周期
活动图业务/算法的流程活动、判断、分叉/汇合（并发）、泳道工作流、跨角色审批流

订单状态图（状态图记法示例）：

[*] ─▶ 已下单 ─付款成功─▶ 已付款 ─发货─▶ 已发货 ─签收─▶ 已完成 ─▶ [*]
         │                                              │
         └──────────── 取消 ────────────▶ 已取消 ◀───────┘

借书用例对应的序列图片段（消息自上而下按时间排列）：

读者              借阅控制对象           D1 读者库
 │──借书(书号)───▶ │                      │
 │                 │────校验证件()──────▶ │
 │                 │◀───读者有效────────── │
 │                 │ (检查库存→创建借阅记录) │
 │◀──借书回执───── │

三图辨析陷阱：消息箭头看时间轴 → 序列图；问「对象处于什么状态、什么事件触发迁移」→ 状态图；有泳道、有并发分叉/汇合 → 活动图。序列图的返回消息是虚线箭头，别与同步消息画混。

四、设计模式：意图对号入座

设计模式按目的分三类：创建型（怎么造对象）、结构型（怎么组装）、行为型（怎么协作）。高频八个：

模式类一句话意图
单例 Singleton创建保证一个类只有一个实例，提供全局访问点
工厂方法 Factory Method创建定义创建接口，把实例化推迟到子类
抽象工厂 Abstract Factory创建创建一系列相关产品族，不指定具体类
适配器 Adapter结构转换接口，让不兼容的类协同工作
装饰器 Decorator结构动态叠加职责，比继承更灵活
代理 Proxy结构控制对原对象的访问（延迟加载/权限/远程）
观察者 Observer行为一对多依赖，状态变化自动通知所有订阅者
策略 Strategy行为封装算法族使其可互换，运行期切换

场景速配（上午题基本是给场景选模式）：运行期切换排序/支付算法 → 策略；全局只要一个配置实例 → 单例；不想 new 具体类、由子类定 → 工厂方法，一族相关产品 → 抽象工厂；复用旧接口不兼容的类 → 适配器；给流层层包上缓冲/压缩 → 装饰器；控制访问或延迟开销 → 代理；订阅通知（事件总线）→ 观察者。

下午案例带法：UML 大题常给类图挖空（补多重度/关系线）或给序列图挖消息。先读说明圈「谁用谁、谁包含谁」，再按第二节的记法表连线；多重度按业务规则数（一个读者可发起 0..* 条借阅，一条借阅只对应 1 个书目）。
