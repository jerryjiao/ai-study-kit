# 存量项目升级走探测引导（F13 + kit-version.json），不靠静默降级

2026-09-14 grill 审计发现：v0.1.0→v0.13.1 十七个版本的 CHANGELOG 从未回答「老项目怎么升级」，一贯模式是每版声明向后兼容、把升级责任 implicit 化为运行时容错。代码层数据兼容确实好（progress 新 key 全可选、主题可选文件缺失全回退，「不崩不丢数据」是已达成的硬承诺），但静默降级让用户永远不知道自己少了什么，且有两个流程层真缺口：kit 代码版本漂移无检测（skill 默认项目里的 kit 与 skill 同代，插件更新不更新已拷出的 kit），F1 对已存在目录行为未定义（无条件 `cp -r`，macOS 嵌套拷成 `kit/kit`，存量项目被误路由进 F1 正好撞上）。拍板：**兼容承诺 = 全功能对齐**——功能层从「静默降级」改为「降级必告知 + 给补齐路径」。实施在 v0.14（#44）发版之后（spec：#55）。

> **实施附注（2026-09-14，实施时补记）**：本 ADR 定稿拟名升级流程为「F12」；同日收官的 v0.14（#44-51）已把 F12 编号给了知识图谱投影流程并随插件与四语文档发出，编号不可收回——升级流程顺延为 **F13**，语义与本文完全一致。

## Considered Options

- **维持静默降级（现状）**——拒：降级本身没错，错在用户不知情；掌握度退纯题维度、口头弱信号恒 0 这类降级用户永远感知不到，等于功能发了没发。
- **不承诺升级，大跨度更新建议重建项目**——拒：数据明明兼容，弃之浪费；伤「装了插件就一直好用」的体验。
- **只写文档升级指南**——拒：把多步操作押在执行 agent 的自觉上，正是现状出问题的原因；漂移要进体检才能日常暴露。
- **发版前老快照升级演练制度化**——缓：每次发版多几分钟，真出过一次升级事故再上，不为想象中的问题付成本。

## Consequences

- kit 快照新增版本标记 `kit-version.json`（sync-plugin 打包时写入，F1 拷贝自然带进用户项目）；存量项目「无此文件」本身成为可识别信号（版本未知，按最老处理）。
- F1 语义变更：从「无条件从零初始化」变「第 0 步先探测后分支」——kit 目录已存在（含无版本文件的存量项目）一律转 F13「升级」流程，绝不盲拷。
- study-doctor 检查面从内容新鲜度扩展到代码代际：版本漂移 + 契约完整性两项探测，只报事实与补法。
- CHANGELOG 新增固定栏目「升级与存量影响」（新文件/新契约、老项目缺了会怎样、怎么补、是否破坏性），发版流程多一步必填。
- 边界：v0.14 新数据文件（oral-attempts.json / graph-map.json）不进升级流程，沿用「首用时自建、只读不建」惯例；不写自动迁移脚本，补齐走 agent 带做。
